# 从发送消息到存下一张图：完整流程

这篇面向第一次看柏宝绘源码的人，按实际执行顺序讲一条链路：用户发一条消息，到最终一张图落盘并显示在楼层里。全篇尽量先用文字说清"这一步在做什么"，代码只作为一句"长这样"的佐证，不逐一罗列函数。

整条链路分成两半。前半段由插件在聊天过程中自己跑：判断这一楼有没有值得画的画面，让模型写出提示词，再把提示词塞回正文。后半段由你点击（或自动）触发：把提示词真正发给生图后端，拿到图，存进 SillyTavern 的文件系统。两半之间靠 SillyTavern 的渲染事件和一串 `bbi_image` 标签衔接。

> 关于范围：SillyTavern 本体（发送消息、调用主 LLM 生成正文、渲染楼层）的源码不在本仓库里，插件只能通过事件和 DOM 这两层约定参与。凡是触及 ST 内部的环节，本文都会明确标注"由 ST 负责，仓库内无法确认"。

---

## 一、用户发完消息之后，插件怎么知道该干活了

用户点发送之后，正文由 SillyTavern 自己生成并渲染，这部分代码不在本仓库里，插件看不到过程，只能等事件。它等的是两个事件：生成开始时收到 `GENERATION_STARTED`，就先"上膛"，记住这次生成属于哪个聊天、哪种类型；等这一轮真正结束、AI 楼层渲染出来时收到 `CHARACTER_MESSAGE_RENDERED`，再确认是不是同一轮，是的话才安排分析。

```ts
// 上膛（过滤掉 dryRun、quiet、impersonate 这类不真实的生成）
beginGeneration(chatId, type, dryRun);
// 最终渲染时配对成功，才真正开跑
const matched = consumeGeneration(chatId, type);
if (matched) scheduleForGeneratedFloor(floor, chatId);
```

这里有个容易踩的坑，代码里专门注释过：生成结束事件 `GENERATION_ENDED` 不能用来"卸载膛"，因为 SillyTavern 可能先发它、后发最终渲染。这条结论是从实际运行里总结出来的，不是从 ST 源码里读到的。

自动触发只有这一条路。用户在楼层按钮上手点、或者在卡片上点重绘，是另外的入口，最后会走到同一个分析函数。

## 二、决定"这一楼画不画"，并让模型写提示词

真正干活的是那个分析函数（`src/autoTag/runner.ts`）。它一进来先过一串闸门，检查插件本身有没有启用、自动 tag 开关有没有开、这个角色是不是在排除名单里、这一楼是不是"剧情楼"。

```ts
if (!isAiStoryMessage(message)) return;           // 用户楼、ST 系统楼跳过
if (hasImageTagTrace(source) && !replace) return; // 已经有 tag 就不重复写
```

"剧情楼"的判断只有一份（`src/st/context.ts` 的 `isAiStoryMessage`），被 `/hide` 隐藏的普通楼也算，因为它只是不进提示词，不代表不是剧情。

过了闸门之后，它会拼一份发给模型的请求。内容的组织顺序是固定的：破限提示、角色卡、玩家设定、世界书、后端规范、输出协议、思维链，最后是正文。正文里每个段落后面会带一个人工标记（像 `⟦P1⟧`），让模型能说"我要插在第 3 段后面"。

模型要返回一个 JSON，里面有两块东西：`images` 是选中的画面和它们的提示词，`changes` 是角色外貌档案的变化（比如某个角色第一次出场，要建档）。角色外貌库的做法是让模型直接照抄库里的字段，比如库里写 `long black hair` 就原样写，不再用 `@角色名` 去占位。

发给哪个模型有两种选择：如果配置了专门的"副 API 渠道"，就走 ST 的服务端代理；没配就跟主对话用同一个 API。返回的文本会被严格解析，结构不对就当这次失败，按设置重试几次。

## 三、提示词怎么变成正文里的标签

模型返回的提示词不会直接显示出来，而是被包装成一个自定义标签写回正文。每个画面一条，形如：

```html
<bbi_image>1girl, classroom, sunset
  <nl>...</nl>
  <negative>...</negative>
  <size>portrait</size>
</bbi_image>
```

在写回之前，插件还会做一件重要的事：把插入位置从"分析开始时的正文"重新对应到"此刻真正的正文"。因为分析要花几秒，这段时间里别的插件可能翻译、润色或者追加了内容，如果拿旧快照覆盖就会把别人的修改冲掉。所以它按段落做文本比对，把位置平移到当前正文，再插进去。

写回本身带一层身份校验：聊天、消息、swipe 只要变了就放弃，但正文内容不参与校验，内容差异交给上一步的重定位处理。这就是它能和其它改正文的插件共存的原因。

标签在写回之前会先给每个画面挂一个"自动出图"的标记，表示"这一楼新增了画面，等下记得自动去生成"。写回之后 SillyTavern 会重新渲染这一楼。

顺带说明标签的两个"永不"：它永远不会出现在聊天界面上，也永远不会进入发给模型的提示词。插件注册了两条托管正则做到这一点（`src/st/imageTagRegex.ts`），显示时把它换成一个空锚点，提示词里把它换掉。

---

## 四、标签怎么变成楼层里的卡片

界面上的卡片不是在写标签的时候建的，而是渲染之后由"水合"过程挂上去的。插件监听楼层渲染和更新事件，然后做三件事：从消息原文里解析出所有标签，在楼层 DOM 里找到对应的锚点（就是上一条正则留下的空 `div`），然后按顺序一一配对。

```ts
const tags = parseImageTags(message.mes);
const anchors = [...mesText.querySelectorAll('div[data-bbi-slot]')];
// 第 0 个标签配第 0 个锚点，每个锚点各自挂一张卡片
```

卡片挂在自己的 shadow DOM 里，这样聊天的全局样式和美化主题改不到它，也不怕互相污染。每张卡片挂载时读一下消息的 `extra`，看这个画面的提示词以前有没有出过图，从而决定显示"待生成""已有图"还是"旧提示词"。

这里还有一层兜底值得知道：SillyTavern 有几条路径会直接重写楼层 DOM 却不发任何事件，锚点连同卡片会被一起删掉，事件监听完全无感。所以插件还挂了一个 `#chat` 的观察器，定期给已挂载的卡片做体检，发现锚点掉了就重新挂。观察器只订阅子节点变化，不订阅属性变化，免得自己的改动又唤醒自己。

---

## 五、卡片怎么触发一次出图

如果刚才写了标签而且开了自动出图，卡片一挂载就会看到那个标记，然后自动开始。没开自动出图、或者你只是点某个卡片，走的是同一个生成函数。

```ts
const mode = consumeAutoGenerate(chatId, messageId, swipeId, seq); // 标记只消费一次
if (mode && shouldAutoGenerate(mode, phase)) generate();
```

生成开始时，卡片会先把这次要用的参数就地取一份快照（提示词、负面词、角色、画幅方向等）。为什么要快照：出图期间只要同楼有另一张图生成完，整楼卡片会被重建一次，那时候再去读组件的属性就不靠谱了。同时它会在一个模块级的运行态里登记"这个槽位在生成中"，并拿到一张"任务票据"，后面所有的回调和落盘都靠这张票据认领，防止被取消的旧任务回来改错状态。

## 六、出图的公共中段：闸门与后端分派

真正的出图中段被单独抽了出来（`src/generate.ts`），楼层卡片和对外公开接口共用一份。它先确认后端配置齐了，然后按当前选择分派到 NAI 或 ComfyUI。

```ts
if (isNai) release = await acquireNaiSlot(signal); // 抢并发槽
...
} finally { release?.(); }                          // 无论成败都还槽
```

这一步的关键是"闸门不能绕过"。NAI 的生图接口是阻塞式的，服务端没有排队，如果并发压过去很容易吃限流。所以 NAI 必须先在闸门里排队，还需要遵守一个全局的最小请求间隔，限流时给整个闸门加冷却退避。ComfyUI 不需要这套，因为它自己就有服务端队列。这里还会顺手落实"画幅锁"：如果渠道里锁了横图或竖图，这一次就统一用那个方向。

---

## 七、两家后端各自怎么把图拿到

NAI 这边，先把提示词、画师串、vibe 参考、尺寸和采样参数拼成一个请求体，然后直接 POST 到生图接口。返回的是一个压缩包，插件解开取第一张图，转成可直接显示的地址。整个"发请求加解包"会被包一层重试，遇到 429 或 5xx 退避后再来，配置类错误就立刻报错。

ComfyUI 这边，先把工作流模板渲染成可提交的 JSON。你的工作流可以是"简易参数"模式，也可以是带 `%prompt%` 这类占位符的自定义工作流。提交后拿到一个任务 id，然后轮询它是否跑完，跑完再去取图。请求优先走浏览器直连，只有当请求根本没送到后端（跨域被拦或拒连）时才回退到 ST 服务端转发。

```ts
const promptId = await queueDirect(conn, workflow, signal); // POST /prompt
return await pollDirectResult(conn, promptId, signal);      // 轮询 history，再取 view
```

## 八、图怎么存下来

拿到图之后，先做一次自检：如果这个任务已经被取消或被新的任务取代了，就直接把图丢掉，不要写进聊天记录，否则会把旧提示词的结果错记进去。确认还是当前任务，才真正落盘。

存储分三层。图片本体进 SillyTavern 的 `user/images`，按角色名分个小目录。同时在 `user/files` 写一份同名的 json 侧写，里面存着这条提示词的原文和出图参数，专门给图库跨聊天浏览时读。最后，把一条指针写进这条消息的 `extra` 里。

```ts
// extra 里的结构大致是：按 swipe 分桶，再按提示词哈希分桶，桶里是一串历史
{ [swipeId]: { [promptHash]: [ { path, seed, meta, ... } ] } }
```

指针的写入用的是一个读改写循环：先看当前结构，写回前确认没有被别的地方同时改过，冲突就重试。文件先存、指针后写，这样最坏情况只是多一个没人引用的图片文件，而不会留下一个指向空文件的破指针。

存完图、写好指针之后，插件清掉运行态，再重新水合一次这一楼。卡片这时候会从 `extra` 里读回结果，状态变成"已有图"，把图片显示出来。

---

## 总结

用户发送消息，SillyTavern 生成并渲染正文，插件在生成开始时上膛、在最终渲染时配对，开始分析这一楼。分析会过一串闸门，拼好上下文发给模型，拿到画面和提示词后，先把插入位置重定位到当前正文，再包装成 `bbi_image` 标签写回去，顺便给每个画面挂一个自动出图标记。渲染之后，托管正则把标签换成空锚点，水合过程把锚点和卡片配上，卡片读到标记就自动触发生成。生成时卡片先快照参数、登记运行态、拿一张任务票据，然后进入公共的出图中段：NAI 排队过闸门再直连生图，ComfyUI 提交工作流再轮询取图。图拿到后自检任务是否还有效，有效就上传图片、写侧写、把指针写进 `extra` 并保存聊天，最后清运行态、重新水合，卡片从消息数据里恢复成"已有图"。

---

## 有几处代码里看不到，只能如实说明

- SillyTavern 内部的发送、生成、渲染过程，本仓库没有它的源码，插件只依赖事件和 DOM 这两层约定。
- 事件派发的准确顺序，比如结束事件是否总在最终渲染之前，代码里是注释记录的经验，不是可验证的契约。
- ComfyUI 和 NAI 服务端自己的排队、执行和限流行为，只能从客户端发的协议反推。
- 那些 `/api/images`、`/api/files` 接口的服务端实现，插件这边只写了调用约定。
